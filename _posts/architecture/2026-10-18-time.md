## 1. 금융 IT 시스템에서 시간 타입이 중요한 이유

금융 IT 시스템에서 시간 데이터 관리는 단순한 날짜 기록을 넘어 **거래의 정합성, 처리 순서, 감사 추적 및 금융 상품의 정확성**과 밀접하게 연결되어 있습니다.

주식 거래나 결제 승인에서는 밀리초(ms) 이하의 시간 차이가 거래 결과에 영향을 줄 수 있으며, 글로벌 금융 서비스에서는 시차나 서머타임(DST) 처리 오류로 결제일과 만기일이 달라질 수 있습니다.

금융 시스템에서 시간 타입이 중요한 이유는 다음과 같습니다.

### 1.1 초고속 거래(HFT)의 순서 보장

고빈도 매매(HFT, High-Frequency Trading)에서는 짧은 시간 동안 수많은 주문이 발생합니다. 가격 우선·시간 우선 원칙이 적용되는 시장에서는 동일한 가격의 주문이라도 접수 순서에 따라 체결 우선순위가 달라집니다.

따라서 마이크로초(μs) 또는 나노초(ns) 수준의 시간 표현이 필요할 수 있습니다. 다만 시간 타입의 정밀도만으로 거래 순서가 보장되는 것은 아니므로 시퀀스 번호와 시계 동기화 체계도 함께 고려해야 합니다.

### 1.2 글로벌 시장의 시차 관리

뉴욕, 런던, 도쿄 등 세계 금융시장은 서로 다른 시간대를 사용합니다. 동일한 거래라도 지역에 따라 표시되는 날짜와 시각이 달라집니다.

따라서 거래 발생 시점은 **UTC(협정 세계시)를 기준으로 일관되게 관리**하고, 영업일이나 마감 시각을 계산할 때 해당 지역의 시간대를 적용하는 것이 유리합니다.

### 1.3 거래의 정합성과 감사 추적(Audit Trail)

금융 거래에서는 요청, 승인, 처리 시점을 정확하게 기록해야 합니다. 시간이 잘못 기록되면 거래 이력 분석이나 장애 추적이 어려워질 수 있습니다.

다만 시간 데이터만으로 중복 거래를 방지할 수는 없습니다. 실제 시스템에서는 거래 고유 식별자, 멱등성 키(Idempotency Key), DB 제약조건 등을 함께 활용해야 합니다.

### 1.4 서머타임(DST)과 윤초(Leap Second)

서머타임이 적용되는 지역에서는 특정 현지 시각이 존재하지 않거나 두 번 나타날 수 있습니다. 따라서 지역별 거래 마감이나 배치 작업을 실행할 때 시간대 규칙을 고려해야 합니다.

또한 정밀한 시간 동기화가 필요한 시스템에서는 윤초 처리 방식과 서버의 시간 동기화 정책도 검토해야 합니다.

### 1.5 이자 계산 및 만기일의 정확성

금융 상품의 이자와 만기일은 윤년, 월말, 공휴일 및 영업일 정책에 영향을 받습니다.

따라서 단순히 경과 시간을 계산하는 것과 달력 기반 날짜를 계산하는 것을 구분해야 하며, 이자 계산에는 `LocalDate`와 금융 상품별 일수 계산 규칙(Day-count Convention)을 함께 고려해야 합니다.

## 2. Instant

`Instant`는 UTC 기준 타임라인상의 **특정 순간을 표현하는 Java 시간 클래스**입니다.

1970년 1월 1일 00:00:00 UTC를 기준으로 경과한 초와 나노초를 사용하며, 이를 에포크(Epoch) 기준 시간 표현이라고 합니다.

`Instant`는 날짜와 시각을 사람이 읽기 쉽게 표현하기보다는 특정 사건이 발생한 시점을 기록하고 비교하는 데 적합합니다.

예를 들어 결제 승인, 계좌 이체, 서버 로그 및 이벤트 발생 시각 등에 활용할 수 있습니다.

### 장점

- **시간대 독립성:** 지역 시간대와 관계없이 동일한 시점을 표현할 수 있습니다.
- **명확한 시간 비교:** 시점의 전후 관계와 경과 시간을 비교하기 쉽습니다.
- **시스템 간 일관성:** 분산 시스템과 글로벌 서비스에서 공통된 시간 기준을 사용할 수 있습니다.

### 단점

- **낮은 직관성:** 사용자에게 날짜와 시각을 표시하려면 시간대 변환이 필요합니다.
- **달력 연산의 제약:** 영업일이나 월 단위 날짜 계산에는 적합하지 않습니다.

### 언제 사용할까?

거래 승인 시각, 이체 처리 시각, API 요청 시각, 이벤트 생성 시각 등 **정확한 사건 발생 시점**을 기록할 때 사용합니다.

### 주요 메서드

| 메서드 | 설명 |
|---|---|
| `now()` | 현재 시점 반환 |
| `ofEpochSecond(long)` | 에포크 초로 객체 생성 |
| `getEpochSecond()` | 에포크 초 반환 |
| `plusSeconds(long)` | 지정한 초 더하기 |
| `toEpochMilli()` | 에포크 밀리초 반환 |
| `atZone(ZoneId)` | ZonedDateTime으로 변환 |

### 코드

```java
import java.time.Instant;
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class InstantMain {
    public static void main(String[] args) {

        // 현재 시점
        Instant now = Instant.now();
        System.out.println(now);

        // 에포크 기준 시간
        Instant epoch = Instant.ofEpochSecond(0);
        System.out.println(epoch);
        // 1970-01-01T00:00:00Z

        // 1시간 더하기
        Instant later = epoch.plusSeconds(3600);
        System.out.println(later);
        // 1970-01-01T01:00:00Z

        // 서울 시간대로 변환
        ZonedDateTime seoul =
                later.atZone(ZoneId.of("Asia/Seoul"));

        System.out.println(seoul);
        // 1970-01-01T10:00+09:00[Asia/Seoul]
    }
}
```

`Instant`를 `ZonedDateTime`으로 변환해도 실제 시점은 변경되지 않으며, 해당 지역의 날짜와 시각으로 표현 방식만 달라집니다.

### 금융 시스템에 도입할 때 주의할 점

**1. 타임존 변환**

거래 발생 시점은 UTC 기준으로 관리하되, 영업일과 마감 시각은 금융기관이 정한 시간대를 적용해야 합니다. UTC 날짜를 그대로 회계일로 사용하면 날짜가 잘못 계산될 수 있습니다.

**2. DB 정밀도 차이**

Java의 `Instant`는 나노초 정밀도를 지원하지만, Oracle의 `TIMESTAMP(6)`은 마이크로초 단위까지 저장합니다. 따라서 DB 저장 과정에서 정밀도 차이로 일부 정보가 손실될 수 있습니다.

**3. 금융 영업일 계산**

'3영업일 후 결제'와 같은 요구사항은 단순히 72시간을 더하는 것으로 해결할 수 없습니다. `LocalDate`로 변환한 뒤 공휴일과 영업일 정책을 적용해야 합니다.

**4. API 직렬화**

REST API나 Kafka에서 시간 데이터를 전달할 때는 ISO-8601 형식이나 에포크 밀리초 등 표현 방식을 명확하게 정의해야 합니다.

```text
2026-10-16T14:35:00Z
```

## 3. ZonedDateTime

`ZonedDateTime`은 날짜와 시각에 **지역 시간대(ZoneId) 정보까지 포함하는 불변 객체**입니다.

`Instant`가 절대적인 순간을 표현한다면, `ZonedDateTime`은 해당 순간이 특정 지역에서 몇 시에 해당하는지를 표현합니다.

예를 들어 한국과 뉴욕의 시각은 다르지만 같은 순간을 나타낼 수 있습니다.

```text
서울: 2026-10-16T23:00+09:00
뉴욕: 2026-10-16T10:00-04:00
```

두 값 모두 UTC 기준 `2026-10-16T14:00:00Z`에 해당합니다.

또한 지역별 시간대 규칙을 적용하므로 서머타임(DST)을 고려한 날짜와 시각 계산에 적합합니다.

### 장점

- **시간대 정보 포함:** 지역별 날짜와 시각을 정확하게 표현할 수 있습니다.
- **서머타임 반영:** 지역 시간대 규칙에 따라 DST를 처리합니다.
- **지역 기반 일정 관리:** 국가별 영업시간과 거래 마감 시각 계산에 적합합니다.

### 단점

- **복잡한 시간 연산:** DST 전환 시 특정 현지 시각이 중복되거나 존재하지 않을 수 있습니다.
- **DB 저장 시 정보 손실:** DB 컬럼에 따라 원래의 `ZoneId`가 보존되지 않을 수 있습니다.

### 언제 사용할까?

해외 주식시장 개장 및 마감 시각, 글로벌 금융 서비스의 지역별 예약, 국가별 영업시간 등을 관리할 때 사용합니다.

### 주요 메서드

| 메서드 | 설명 |
|---|---|
| `now(ZoneId)` | 지정한 시간대의 현재 시각 반환 |
| `getZone()` | 시간대 ID 반환 |
| `getOffset()` | UTC 오프셋 반환 |
| `withZoneSameInstant()` | 동일한 순간을 다른 시간대로 변환 |
| `withZoneSameLocal()` | 현지 시각을 유지하면서 시간대 변경 |
| `toInstant()` | Instant로 변환 |

### 코드

```java
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class ZonedDateTimeMain {
    public static void main(String[] args) {

        // 서울 시간
        ZonedDateTime seoul = ZonedDateTime.of(
                2026, 10, 16, 23, 0, 0, 0,
                ZoneId.of("Asia/Seoul")
        );

        // 뉴욕 시간으로 변환
        ZonedDateTime newYork =
                seoul.withZoneSameInstant(
                        ZoneId.of("America/New_York")
                );

        System.out.println(seoul);
        // 2026-10-16T23:00+09:00[Asia/Seoul]

        System.out.println(newYork);
        // 2026-10-16T10:00-04:00[America/New_York]

        // 동일한 순간인지 확인
        System.out.println(seoul.isEqual(newYork));
        // true
    }
}
```

`withZoneSameInstant()`는 실제 시점을 유지하면서 시간대만 변환합니다.

### 금융 시스템에 도입할 때 주의할 점

**1. DB 저장 시 시간대 정보 유실**

모든 DB 타입이 `Asia/Seoul`과 같은 지역 시간대 ID를 보존하는 것은 아닙니다. 따라서 원래 지역 정보가 중요하다면 시각과 `ZoneId`를 별도로 저장하는 방식을 고려해야 합니다.

**2. 시간 비교**

`ZonedDateTime`의 `equals()`는 시간대 정보까지 비교하므로 동일한 순간이라도 `false`가 반환될 수 있습니다.

실제 시점의 비교에는 `isBefore()`, `isAfter()`, `isEqual()` 등을 사용하는 것이 적절합니다.

**3. 서머타임에 따른 배치 오류**

서머타임 전환 시 특정 현지 시각이 존재하지 않거나 중복될 수 있습니다. 따라서 지역별 배치 작업은 시간대 규칙과 스케줄러의 DST 처리 정책을 함께 검토해야 합니다.

## 4. LocalDateTime

`LocalDateTime`은 연도, 월, 일, 시, 분, 초, 나노초 정보를 포함하지만 **시간대와 UTC 오프셋은 포함하지 않는 Java 시간 클래스**입니다.

예를 들어 다음 값은 날짜와 시각만 나타냅니다.

```text
2026-10-16T15:30:00
```

이 값이 한국 시간인지 미국 시간인지 알 수 없으므로, `LocalDateTime`만으로는 절대적인 거래 시점을 확정할 수 없습니다.

### 장점

- **직관적인 표현:** 사람이 사용하는 날짜와 시각을 직접 다룰 수 있습니다.
- **간단한 날짜 연산:** 일, 월, 시간 단위 연산이 가능합니다.
- **시간대 독립적인 표현:** 특정 지역에 연결되지 않은 현지 날짜와 시각을 나타낼 수 있습니다.

### 단점

- **절대적인 시점 표현 불가:** 시간대 정보가 없어 거래 발생 시점을 단독으로 확정할 수 없습니다.
- **시간대 변환 필요:** `Instant`로 변환하려면 `ZoneId` 또는 `ZoneOffset`이 필요합니다.
- **서머타임 미반영:** DST에 따른 시간 변화를 자체적으로 처리하지 못합니다.

### 언제 사용할까?

특정 지점의 예약 시각이나 운영자가 설정한 현지 마감 시각처럼 날짜와 시각을 먼저 표현하고, 시간대는 별도 규칙으로 관리하는 경우에 적합합니다.

### 주요 메서드

| 메서드 | 설명 |
|---|---|
| `now()` | 현재 현지 날짜와 시각 반환 |
| `of(...)` | 지정한 날짜와 시각으로 생성 |
| `plusDays(long)` | 지정한 일수 더하기 |
| `minusDays(long)` | 지정한 일수 빼기 |
| `atZone(ZoneId)` | ZonedDateTime으로 변환 |
| `toLocalDate()` | 날짜 정보 추출 |

### 코드

```java
import java.time.Instant;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class LocalDateTimeMain {
    public static void main(String[] args) {

        // 날짜와 시각 생성
        LocalDateTime local = LocalDateTime.of(
                2026, 10, 16, 15, 30
        );

        // 하루 뒤
        LocalDateTime tomorrow = local.plusDays(1);

        // 서울 시간대 적용
        ZonedDateTime seoul =
                local.atZone(ZoneId.of("Asia/Seoul"));

        // UTC 기준 시점으로 변환
        Instant instant = seoul.toInstant();

        System.out.println(tomorrow);
        // 2026-10-17T15:30

        System.out.println(instant);
        // 2026-10-16T06:30:00Z
    }
}
```

`LocalDateTime`을 절대적인 시점으로 변환하려면 어떤 지역의 날짜와 시각인지 명확히 지정해야 합니다.

### 금융 시스템에 도입할 때 주의할 점

**1. 거래 발생 시점 저장**

`LocalDateTime.now()`는 시스템 기본 시간대를 사용하므로 서버 환경이 달라지면 기록되는 현지 시각도 달라질 수 있습니다.

따라서 거래 승인이나 이체 처리처럼 절대적인 시점이 중요한 데이터는 `Instant` 등을 사용하는 것이 적합합니다.

**2. 만기일 및 마감 시각**

금융 상품의 만기일이나 거래 마감 시각은 금융기관의 시간대 정책에 따라 달라질 수 있습니다. 따라서 실제 시점을 계산할 때는 `ZoneId`를 적용해야 합니다.

**3. DB 연동**

Oracle의 일반적인 `TIMESTAMP`는 시간대 정보를 포함하지 않습니다. 따라서 `LocalDateTime`을 저장할 때는 애플리케이션에서 해당 값의 시간 기준을 명확하게 정의해야 합니다.

## 5. 시간 클래스 비교하기

Java의 시간 타입을 선택할 때 가장 중요한 기준은 **해당 데이터가 절대적인 사건의 순간인지, 특정 지역의 날짜와 시각인지** 구분하는 것입니다.

### 5.1 주요 시간 클래스 비교

| 클래스 | 시간대 정보 | 주요 용도 |
|---|---|---|
| `Instant` | 지역 시간대 없음 | 거래 발생 시점, 로그, 이벤트 |
| `ZonedDateTime` | ZoneId 포함 | 지역별 영업시간, DST 처리 |
| `LocalDateTime` | 없음 | 현지 예약 시각, 시간대가 별도로 정의된 일정 |
| `OffsetDateTime` | ZoneOffset 포함 | 오프셋이 명시된 API 통신 |
| `LocalDate` | 없음 | 영업일, 만기일, 생년월일 |

`OffsetDateTime`은 `+09:00`과 같은 고정된 오프셋을 사용하고, `ZonedDateTime`은 `Asia/Seoul`과 같은 지역 시간대 규칙을 포함한다는 차이가 있습니다.

### 5.2 실무에서 발생할 수 있는 문제

**배포 이후 시간이 9시간 차이 나는 경우**

개발 서버는 KST, 운영 서버는 UTC를 사용하는 환경에서 `LocalDateTime.now()`를 호출하면 서로 다른 현지 시각이 기록될 수 있습니다.

**일별 집계 결과가 다른 경우**

UTC 자정과 KST 자정은 서로 다른 순간입니다. 따라서 거래 집계 시 기준 시간대를 명시해야 합니다.

**자정 전후에 조회 오류가 발생하는 경우**

날짜 경계 처리 오류로 데이터가 누락되거나 중복될 수 있습니다. 다음과 같이 시작 시각은 포함하고 종료 시각은 제외하는 조건을 사용하는 것이 유리합니다.

```sql
WHERE CREATED_AT >= :startTime
  AND CREATED_AT < :endTime
```

종료 시각을 다음 날 자정으로 지정하면 시간 정밀도에 따른 경계 오류를 줄일 수 있습니다.

### 5.3 금융 시스템의 데이터 타입 권장안

| 데이터 성격 | 추천 타입 |
|---|---|
| 결제 승인 및 이체 발생 시점 | `Instant` |
| 해외 시장 개장 및 마감 시각 | `ZonedDateTime` |
| 오프셋이 포함된 API 시각 | `OffsetDateTime` |
| 금융 상품 만기일 | `LocalDate` |
| 현지 예약 시각 | `LocalDateTime` + `ZoneId` |
| 서버 로그 및 이벤트 시각 | `Instant` |

## 6. 결론

금융 IT 시스템에서 시간 타입을 선택하는 것은 단순한 날짜 저장 문제가 아니라 **거래의 정확성과 시스템 간 일관성을 확보하기 위한 설계 과정**입니다.

`Instant`는 절대적인 거래 시점을 기록하는 데 적합하고, `ZonedDateTime`은 지역별 시간대와 서머타임을 고려할 때 유용합니다. 반면 `LocalDateTime`은 시간대가 포함되지 않은 날짜와 시각을 표현하는 데 적합합니다.

따라서 모든 시간 데이터를 하나의 타입으로 통일하기보다, 데이터의 의미와 비즈니스 요구사항에 따라 적절한 타입을 선택해야 합니다.

또한 실제 금융 시스템에서는 DB 정밀도, 서버 시간 동기화, 영업일 정책, API 직렬화 방식 등을 함께 고려해야 합니다.

**중요한 것은 어떤 시간 클래스를 사용하는지가 아니라, 해당 시간이 무엇을 의미하며 시스템 전체에서 어떻게 관리되는가입니다.**
